orbit-launcher · design presentation v0.1

A full-screen terminal app, not a fancier script

This replaces the bash-script command-centre approach from issue #260 (orbit/orbit#260) entirely. orbit-launcher is a dedicated terminal application: true full-screen control of the terminal, an animated starfield behind a static Orbit mark, and a small, confident set of choices — not a menu tree bolted onto install.sh. It also adds something #260 never had: a real way out — Remove stops Orbit and hands back a copy-pasteable command for anyone who decides it isn't for them, instead of leaving them to figure out docker and file paths on their own.

Suggested stack: Go, with charmbracelet/bubbletea for the full-screen event loop and charmbracelet/lipgloss for layout/styling — the same toolkit behind gum and glow, built exactly for this. The starfield renders as Unicode dots/braille on a tick-driven animation frame, true-colour via 24-bit ANSI everywhere; on terminals that support the Kitty or Sixel graphics protocol (Kitty, WezTerm, Ghostty, iTerm2) we can optionally render it as a soft blurred image layer for extra depth, falling back cleanly to the character-based version elsewhere.

First impression, one job

  • Banner position — centred left/right, sitting slightly above true vertical middle exactly as you described; the menu hangs directly beneath it so the eye never has to travel far.
  • No box around the mark — floating over the starfield reads as "full screen app," not "dialog in a terminal."
  • Five choices, grouped by intent — Install / Update / Repair manage the deployment; a small gap, then Remove / Exit are the two ways to leave. orbit-launcher detects which of Install or Update applies and could even pre-select it, but both stay visible for clarity.
  • Remove exists on purpose — #260 never had a way out. It's grouped with Exit, not hidden in a submenu, because "I don't want this anymore" deserves to be as easy to find as "I want this."
  • Animation here: starfield drifts slowly (parallax — distant dots move slower than near ones), individual stars twinkle on a random slow cycle, and a single point of light orbits the ⟡ mark once every few seconds. Nothing on this screen animates fast enough to feel busy.

Decisions, not forms

  • One decision per screen where possible — profile first, without asking for the address or auth details yet, so nothing feels like a wall of fields.
  • Cost is shown inline, not hidden in docs — resource footprint changes with profile, so it's shown the moment it becomes relevant, in muted colour so it reads as context, not a warning.
  • Step indicator top-right keeps orientation without a progress bar competing for attention this early.

Only what's needed, grouped

  • Required fields first, optional service toggles visually separated below a hairline — the eye can stop reading once the required section is filled in.
  • Secrets are masked but present — never hidden behind a separate "advanced" screen; security-relevant fields shouldn't be an afterthought.
  • No animation on this screen beyond a blinking field cursor — this is a moment of focus, the starfield stays off entirely (plain background) so nothing competes with data entry.

The point of no return, made explicit

  • A plain-language commitment line ("Nothing has been installed yet…") rather than relying on the user to infer it from a "Confirm" button — this is the single most important sentence in the whole flow.
  • Full image digest shown, not hidden — matches the existing project's emphasis on immutable, verifiable deployments.
  • Two choices only at this gate: commit, or go back. No third "cancel entirely" needed — esc/Ctrl-C always works.

Never a silent gap

  • This is the direct fix for issue #260's original complaint — no step collapses into a quiet, unexplained pause. Every service gets its own line the moment it starts being checked.
  • Indentation shows hierarchy — "Starting services" is the parent state, its children are the individual health probes, so the structure reads without needing a nested box.
  • Animation: braille spinner frames advance on a steady tick (~120ms) for anything "in progress"; completed lines lock to a static ✓ the instant they finish so the log doesn't feel like it's still moving once it's done. Starfield stays off here — this screen is about status, not atmosphere.

Calm, specific, actionable

  • Muted red, not flashing — the error is serious, the screen shouldn't be alarming. No starfield: this is a moment for plain, still focus.
  • One real reason, not a stack trace — matches the existing project's principle of fixed, non-sensitive reason/action vocabulary, just given more room to breathe on a full screen than a single log line ever could.
  • The reassurance ("nothing on disk has changed") is a direct sentence, not implied — echoes the same honesty as the final-review screen.

Say what will and won't happen

  • Same review-grid pattern as final-review on the way in — consistency here matters: leaving should feel as considered as arriving.
  • The scary part is named and scoped immediately: this step stops things, it does not delete things. That distinction is the whole design, so it's said twice — once in the title, once in the note.
  • Default action is still framed positively ("Stand down Orbit," not "Yes, remove") — plain language over a generic confirm/cancel pair.

The mirror of the install screen, deliberately

  • Reuses the readiness screen's exact visual language (same spinner, same ✓ states) run in reverse — a person who's seen Orbit install already knows how to read this without learning anything new.
  • No starfield, no drama — this is routine maintenance, not an ending. The ending is the next screen.

11 Remove — stood down

orbit-launcher — stood down
✓Orbit has been stood down
Containers and networks are stopped. Your files and data volumes are still on disk at /opt/orbit — nothing has been deleted.
To fully remove Orbit from this machine, copy and run
docker compose -f /opt/orbit/docker-compose.yml down -v \
  && sudo rm -rf /opt/orbit
This deletes all mail, documents, and configuration. It cannot be undone.
▸ Copy commandExit

The app stops; the person decides on the data

  • This is the point of the whole feature. orbit-launcher never runs rm -rf or down -v itself — it only ever does the safe, reversible half automatically. The destructive half is a real, readable command the person chooses to run themselves, in their own shell, on their own authority.
  • The command is exact and copyable (real terminals support OSC 52 clipboard copy over SSH — "Copy command" can genuinely populate the clipboard, not just tell them to select text), scoped to the actual install path, not a generic example.
  • Warning colour used exactly once, on the one sentence that needs it — everything else on this screen stays in the calm, neutral palette.
This is a first pass to align on direction — layouts, palette, and tone — before any Go/Bubble Tea code gets written. Once the direction here is right, next steps would be: a clickable prototype (real Bubble Tea app, keyboard-navigable, starfield actually animated) covering just the splash → install → progress path, then the remaining screens (update detection, repair) once that core feels right.
